# Building and releasing

## Versioning

Clueless uses [semantic versioning](https://semver.org). The app reads its
version from `"version"` in `overlay/package.json`, and so do the DMG filename,
the About tab, `/health` and `--preflight-json`. release-please keeps
`version.txt` and `.release-please-manifest.json` in step with it. Never edit
any of the three by hand.

[release-please](https://github.com/googleapis/release-please) owns version
bumps. It reads Conventional Commit messages on `main`:

| Commit | Bump |
|---|---|
| `fix: …` | patch (0.2.0 → 0.2.1) |
| `feat: …` | minor (0.2.0 → 0.3.0) |
| `feat!: …` or a `BREAKING CHANGE:` footer | major |
| `docs:`, `chore:`, `test:`, `refactor:`, `ci:` | none |

While the version is below 1.0, breaking changes bump the minor version.

## Release flow

1. PRs merge to `main`. `release-please` opens or updates a **release PR**
   that bumps the version and adds to `CHANGELOG.md`.
2. Merging the release PR tags `vX.Y.Z` and publishes a GitHub Release.
3. The same workflow then calls `build-release.yml` for that tag. It is called
   directly, not triggered by the release event, because a release created
   with `GITHUB_TOKEN` doesn't start other workflows. The build runs on a
   `macos-26` arm64 runner:
   1. Builds the Swift helpers, then a relocatable Python
      (`native/build-python.sh`).
   2. Generates `THIRD_PARTY_NOTICES.txt` and fails on a disallowed license.
   3. Runs `electron-builder` to produce the DMG and zip.
   4. Verifies the bundle: valid signature, no `.env` or settings files, no
      `__pycache__`.
   5. Writes `SHA256SUMS.txt` and an SPDX SBOM, and uploads everything to the
      release. Unnotarized builds also get the Open Anyway steps appended to
      their release notes.

To rebuild an existing tag, run **Actions → Build release → Run workflow** with
the tag.

**One-time repository settings:** under **Settings → Actions → General**, allow
GitHub Actions to create pull requests; release-please needs it. CI needs a
`macos-26` hosted runner. If the image isn't available to the repository,
change `runs-on` to a self-hosted Apple-silicon runner on macOS 26.

## Signing and notarization

Releases are **ad-hoc signed** until Apple Developer credentials are added.
Users then have to choose **Open Anyway** in System Settings on first launch;
the README explains how.

Ad-hoc signing is done by `overlay/build/after-pack.js` when
`CLUELESS_ADHOC_SIGN=1`; `npm run dist:unsigned` sets it. An unsigned build
would be worse than an ad-hoc one. Packaging rewrites Electron's `Info.plist`
and breaks its original signature. On Apple silicon, macOS reports a downloaded
app with a broken signature as *damaged*, and offers no way to open it.

The hook signs every Mach-O file inside out, and signs executables with
`entitlements.mac.plist`. Without `disable-library-validation`, the
hardened-runtime `python3` refuses to load its own extension modules.

The workflow signs and notarizes automatically once these repository secrets
exist. No code change is needed:

| Secret | Value |
|---|---|
| `CSC_LINK` | Base64 of a *Developer ID Application* certificate exported as `.p12` |
| `CSC_KEY_PASSWORD` | Its export password |
| `APPLE_API_KEY` | Contents of an App Store Connect API key (`.p8`) |
| `APPLE_API_KEY_ID` | That key's ID |
| `APPLE_API_ISSUER` | The issuer ID shown with it |

With them, the workflow does three things:

- signs the Swift helpers with the same identity (notarization rejects a bundle
  with mixed signers);
- lets electron-builder sign everything else;
- passes `-c.mac.notarize=true`.

## Building a DMG locally

```bash
native/build.sh             # Swift helpers
native/build-python.sh      # relocatable Python 3.12 + locked dependencies
scripts/third_party_notices.sh
cd overlay && npm ci
npm run dist:unsigned       # or `npm run dist` with a signing identity in the keychain
```

The output is `overlay/dist/Clueless-<version>-arm64.dmg`. Opening it shows the
app and an Applications shortcut over a background with an arrow between them.
The background is generated by `scripts/make_dmg_background.swift`, at 1x and
@2x.

To build a quick `.app` for this Mac only, without a DMG, use
`scripts/pack-local.sh`.

## What goes into the bundle

`electron-builder` includes an explicit file list (`build.files` and
`extraResources` in `overlay/package.json`), never the whole directory:

| Included | Excluded |
|---|---|
| `overlay/*.js`, `*.html`, `*.css` | tests, ESLint config |
| `native/build/{CluelessTap.app,ocr,fmcli}` | test binaries (`speechtest`, `fmtest`, …) |
| `native/build/python/` | pip caches, `__pycache__`, test suites |
| `server/**/*.py` | `server/test_*.py` |
| `THIRD_PARTY_NOTICES.txt`, `LICENSE` | `.env`, `.env.*`, `settings.json`, `.chroma/`, logs |

`scripts/pack-local.sh` and the release workflow both fail the build if a file
named `.env`, `.env.signing` or `settings.json` ends up inside the bundle.

## Python runtime

The app doesn't use the system Python. `native/build-python.sh` downloads a
pinned [python-build-standalone](https://github.com/astral-sh/python-build-standalone)
release, checks it against a recorded SHA-256, and installs
`requirements.lock` with `pip install --require-hashes`. Every dependency is
therefore pinned to an exact version and hash. To update:

```bash
pip install pip-tools
pip-compile --generate-hashes --output-file=requirements.lock requirements.txt
```

Commit `requirements.txt` and `requirements.lock` together.

**Never write bytecode into the shipped runtime.** If anything runs
`native/build/python/bin/python3` without `-B` (tests, scripts), it leaves
`__pycache__` folders behind. Packaging excludes them, and the packaged app
points `PYTHONPYCACHEPREFIX` at the data folder, because a file written inside
a signed bundle breaks its signature seal. Note that `-I` ignores
`PYTHONDONTWRITEBYTECODE`; use `-B`.

## Publishing the public repository

The public repository is created from a clean export, not by making a private
history public. Anything ever committed and later deleted stays in a
repository's history. `scripts/publish-oss.sh` works like this:

1. It exports the committed tree (`git archive HEAD`), so untracked, ignored and
   uncommitted files can't leak. It refuses to run with uncommitted changes.
2. It scans the export, and stops on any hit:
   - for credential-shaped files (`.env`, `.p12`, `.p8`, keys), the local notes
     files, and anything over 5 MB;
   - against the `.denylist`, which must exist;
   - with gitleaks.
3. It makes one commit, `feat: initial public release`, authored with your
   GitHub `noreply` address unless you pass `--author`, and tags it with the
   current version.
4. After you type the repository name to confirm, it creates the public
   repository and pushes. It then:
   - enables private vulnerability reporting;
   - allows Actions to open release PRs;
   - publishes the GitHub Release;
   - starts the DMG build.

```bash
scripts/publish-oss.sh --dry-run             # export + scan only; lists every file
gh repo rename clueless-private              # if the public name is taken by this repo
scripts/publish-oss.sh owner/clueless        # create, push, release
```

It refuses to push to this repository's own remote, or into any repository
that already exists.
